# Cloudflare Pages playable deployments

> Hosting contract. The game source remains in this repository. `dist/` and `generated/` are disposable outputs.

## Deployment flow

The `Verify` GitHub Actions workflow runs on pushes to `main` and pull requests. Feature-branch commits are verified through the pull request when it is opened, reopened, or updated, avoiding a duplicate push run for the same change. It checks assets, builds `dist/`, runs the preview smoke test, validates content, runs tests, and checks for source changes. Only after those steps pass does it upload `dist/` as a short-lived workflow artifact. The separate deploy job downloads that artifact without checking out or executing PR code, then sends it to Cloudflare Pages with the official Wrangler action. A failed upload or failed live-site smoke test fails the deploy job in GitHub Actions. The deployed output is never committed.

| Event | Pages branch | Result |
| --- | --- | --- |
| PR from this repository, opened/reopened/updated | `pr-<PR number>` | Preview; the branch alias moves to the latest successful deployment |
| PR from this repository, merged | `pr-<PR number>` | Cleanup; keep the deployment currently owning the stable PR branch alias and delete superseded previews for that PR |
| Push to `main` | `main` | Production, after the same Verify checks pass |
| Push to another branch | none | No push workflow; an open PR update triggers Verify and, for same-repository PRs, the preview |
| PR from a fork | none | Secret-free Verify only; no automatic preview |

The default `pull_request` checkout builds GitHub's proposed merge commit, so a preview represents the PR combined with its current base. On a new commit, the newest workflow run supersedes the previous run. The Cloudflare branch alias `pr-<number>.<project>.pages.dev` stays stable while its target updates. Find the actual URL in the PR's **Deploy Cloudflare Pages** check summary or GitHub Deployment. Each run also records its immutable deployment URL. Do not record a temporary deployment URL in source files.

### Merged PR preview cleanup

The `Cleanup merged PR previews` workflow runs only when a same-repository pull request is actually merged. It lists Cloudflare Pages **preview** deployments, narrows them to the exact synthetic Pages branch `pr-<PR number>`, and keeps the one deployment that currently owns the stable branch alias `pr-<PR number>.<project>.pages.dev`. All other deployments in that exact preview branch are deleted.

The stable alias is the keeper authority rather than `pull_request.head.sha`: PR previews are built from GitHub's proposed merge commit, and the current deploy command records `github.sha`, so the Cloudflare commit hash is not necessarily the PR head SHA. The cleanup is fail-closed: if Cloudflare does not report exactly one deployment owning the expected branch alias, it deletes nothing and fails the job. It never considers production deployments or the `main` branch. Fork PRs and PRs closed without merging are skipped.


Cloudflare Pages serves the static files directly. The game enters at `/` and selects the story via query string; `index.html` sets the URL base to `/`, so a Pages SPA fallback on a deeper path can still find the JS, route JSON, and art. The deployment job fetches the live page, a fallback path, the route package, JS, and an asset after upload. Codespaces and Browser Acceptance remain separate engineering checks.

## One-time account setup

The Pages Direct Upload project for this repository is **`seventeen-floor-neighbor`**, with production branch **`main`** and production domain **`https://seventeen-floor-neighbor.pages.dev/`**. Do not connect it to Git auto-builds; GitHub Actions owns the build and deployment path. The production domain is the public site, while the PR aliases are generated by Pages after each successful preview deployment.

1. If setting up another account, create a **Pages Direct Upload** project with production branch **`main`**. An authenticated Wrangler CLI can create it with `wrangler pages project create` and `--production-branch main`. Use the actual project name shown by Cloudflare. Do not reuse an unrelated or Git-integrated project.
2. Create a Cloudflare API token restricted to the intended account with **Account → Cloudflare Pages → Edit**. Do not grant broader permissions. Find the account ID in Cloudflare.
3. In this GitHub repository, add Actions secrets **`CLOUDFLARE_ACCOUNT_ID`** and **`CLOUDFLARE_API_TOKEN`**. Add an Actions variable **`CLOUDFLARE_PAGES_PROJECT`** containing the exact Pages project name. Never put those values in the repository or workflow logs.
4. Allow GitHub Actions to create deployments using `GITHUB_TOKEN` (the deploy job requests `deployments: write`). Check the first `main` run and a same-repository PR run. Their deploy checks must show success and a playable URL. A missing setting produces a clear failed deploy check.

The project must really have production branch `main`: Wrangler's `--branch=main` becomes production only when this matches the Pages project setting. A Direct Upload project's production branch is account configuration, not a setting in this repo.

## Secret and PR boundary

The Verify job has read-only repository permission and no Cloudflare credentials. Fork PRs never enter the deploy job. The deploy job gets credentials only after Verify succeeds and runs without a checkout; it handles the downloaded static build as data. It rejects an empty/malformed Pages project name and server-side `_worker.js` or `functions` output. The account token is limited to Pages edits in one Cloudflare account. Do not use `pull_request_target` or a `workflow_run` bridge to deploy fork code with credentials. A fork contribution can be reviewed as a same-repository branch after a maintainer intentionally brings it into a trusted branch.

GitHub collaborators who can edit workflows or push branches in this repository are trusted to affect the preview environment; protect `main` and limit write access accordingly. The previews are public by default. If private review is required, configure Cloudflare Access separately for the Pages preview hostname.

## Troubleshooting

- If Verify fails, deployment does not start. Check the failing asset/build/validation/test step first.
- If Deploy fails before upload, check the three GitHub settings, token scope, and the Pages project's production branch. The workflow deliberately does not create account resources.
- If upload succeeds but the smoke test fails, use that run's immutable URL and compare the live route JSON or asset response with `dist/`. The job fails so the problem stays visible in GitHub.
- Cloudflare Pages allows up to 25 MiB per static file. Check asset size before adding large media. The current build copies runtime assets from tracked `assets-src/` files; it needs no Drive download or local cache.
