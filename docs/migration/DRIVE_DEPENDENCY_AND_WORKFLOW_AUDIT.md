# Drive dependency and production workflow audit

> Audit ref: `work/asset-migration-gate1-audit` at `084e7519dfcf76265d192f0a6c3a60042e4a0438` (main baseline)
>
> Scope: dependency and workflow audit only. This records observed paths and required follow-up; it does not change providers or assets. Asset-by-asset inventory and binary migration verification are tracked separately.

## Finding

At this baseline, Google Drive is an active build-time provider and canonical source catalog provider. It is not the browser's direct image loader: the browser consumes same-origin runtime paths embedded in route `assets.json`, and `tools/build-assets.mjs` must first download Drive-backed files into `generated/runtime-assets/`. A clean build therefore depends on network access to Drive even though runtime URLs look local. Separate production-reference acquisition also depends on Drive IDs and pixels.

`npm run validate` passes at the audit baseline: 2 routes, 2 characters, 35 assets/recipes, 180 story nodes, 4 Narrative Continuity Contracts and 8 CG manifest entries. This does not demonstrate an offline build; it does not execute remote asset acquisition.

3. `content/production/cg-manifests/opening-ch1.json` has accepted entries `COM00-S02-DOOR-ASSIST`, `COM00-S04-BASE-NEUTRAL`, and `COM00-S04-R01-POLITE-SMILE`; `node tools/render-cg-packets.mjs --manifest ... --check` validates all 8 entries. The manifest's declared visual references use `gdrive:<file_id>` values (including character/environment refs), resolved through the renderer's explicit Drive resolver.
4. `content/assets/manifest.json` maps corresponding stable runtime IDs `cg.opening.com00.s02_door_assist`, `.s04_base_neutral`, `.s04_r01_polite_smile` and background `bg.opening.ch1.apt_17f_rain` to runtime paths. Those paths are Drive-backed in `source-map.json`; the ingest receipt records original attachment source hashes and Drive runtime IDs/URLs.
5. `content/routes/opening-demo/chapter-01.json` uses these logical IDs through `common_movein_rain_assist`, `_move`, `_choice`, choice branches and names/goodnight nodes. `route.json` explicitly allowlists each ID. `memories.json`, title art, gallery and ending art share those IDs; `tools/content-lib.mjs` validates route assets and memory gallery references.
6. Browser consumes only the built route manifest and same-origin file paths. But `npm run build` first reaches Drive during `build-assets`; therefore the browser path is same-origin while build reproducibility is not.

The contract chain is therefore represented in canonical scene/narrative/manifest/asset/route files, but the run ledger/packet/handoff evidence for this specific scene is absent, and the image reference acquisition step remains tied to Drive.

## Issue #16 overlap and current friction

The existing implementation already has a canonical orchestration DAG, schemas for Task Packet, handoff and generated run ledger, a deterministic `tools/context.mjs`, and manifest projection/hash validation. The practical continuity gap is persistence: no actual run records are present under the declared run root, while packet/handoff content is expected inside that root and not outside the repository. This does not establish that artifacts are being written to a gitignored session cache; the repo currently records the persistent-run convention, not that requested cache policy.

The workflow has deterministic hashes and stale rules in the orchestration document, but the checked validators center on schema/contract consistency rather than an artifact dependency graph with selective invalidation evidence. Task Packet/Handoff schema requires immutable versions but still names Drive IDs as allowable immutable versions. These are observed gaps; implementation should preserve the existing five harnesses and gates.

- No asset deletion recommendation is made in this audit: every delete requires the separate complete usage inventory and verified consumer search.

## Minimum follow-up verification tied to these dependencies

- `assets:check` and `assets:build` with Drive token absent and Drive network denied; assert every gameplay logical ID resolves to a committed, full-decode-valid file and no output is a pointer/placeholder.
- Clean checkout `npm run build`, `npm run validate`, `npm test`, `npm run preview:smoke`; inspect exact `dist/` output, same-origin requests, MIME, cache behavior and no Drive request.
- Inspect the built `dist/` paths and route/Memory/Gallery/Continue asset bindings deterministically. Update old browser assertions only where code or retained regression fixtures actually change; a live browser run is not a migration acceptance condition.
- Machine-injected errors for bad hash, missing file, unapproved asset, unknown logical ID, stale manifest/reference, route/Memory binding, and artifact-level invalidation; verify unrelated scene/entry outputs remain valid.
- Push checkpoint and fresh-session resume using only committed canonical hashes and a new empty session cache. If persistent QA/Human decisions cannot be recovered, require bounded re-review; hash mismatch blocks dispatch.
